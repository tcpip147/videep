# 연구 결과: 차량 분석 플러그인 예제

## 결정 1: GPU 배열 상호운용

**결정**: `torch.from_dlpack(FrameView)`로 GPU 메모리를 공유하고 파이프라인 CUDA 스트림에서 처리한다.

**근거**: PyTorch 공식 DLPack 계약은 변환 텐서가 입력 메모리를 공유한다고 명시하며, DLPack의 consumer stream 전달로 생산자와 소비자 사이를 동기화할 수 있다. PyNvVideoCodec 장치 메모리 프레임도 DLPack 교환을 지원한다.

**검토한 대안**: CuPy는 유효한 무복사 대안이지만 모델 실행과 ROI 처리를 위해 추가 연결이 필요하다. NumPy는 전체 프레임 CPU 전송 때문에 제외한다. 원시 CUDA 포인터 노출은 수명과 피치 계약을 약화한다.

## 결정 2: 모델 실행

**결정**: 차량 검출은 CUDA 텐서 입력을 받는 Ultralytics YOLO, 차급 분류는 별도 PyTorch/TorchScript CUDA 모델, ROI 배치는 `torchvision.ops.roi_align`을 사용한다.

**근거**: 학습 모델을 교체하려는 사용자가 이해하기 쉬우며 검출 입력과 ROI 배치를 GPU에 유지할 수 있다. `eval()`, 추론 모드와 선택적 반정밀도를 사용한다.

**검토한 대안**: TensorRT는 성능 배포용 선택 어댑터로 적합하지만 엔진 빌드와 GPU·버전 호환 관리가 참고 예제의 진입장벽을 높인다. ONNX Runtime은 공급자 및 I/O Binding 어댑터가 추가로 필요하다.

## 결정 3: 단계 간 결과 전달

**결정**: 백엔드 독립적인 프레임별 `FrameArtifacts`를 핵심 런타임에 추가한다.

**근거**: 현재 불변 `FrameView.metadata`는 단계별 결과 전달에 사용할 수 없다. 전역 상태는 동시 프레임 결과를 섞고 수명을 보장하지 못한다. 런타임 소유 저장소가 프레임 식별, 오류 정리와 백프레셔 책임에 부합한다.

**검토한 대안**: 가변 `GpuFrame.metadata`는 불변 프레임 계약과 GPU 버퍼 수명을 표현하지 못한다. 세 단계를 한 플러그인에 합치면 독립 교체 요구를 위반한다.

## 결정 4: GPU 전처리와 표시

**결정**: NV12 변환·크기 조정은 GPU 텐서 연산으로 수행하고, 사각형과 고정 차급 텍스트는 GPU bitmap glyph atlas로 writable 프레임에 합성한다.

**근거**: GPU 내부 변환은 허용하면서 전체 프레임 호스트 왕복을 피한다. 범용 글꼴·이미지 API가 유발할 수 있는 CPU 경로를 제거한다.

**검토한 대안**: CV-CUDA는 Linux의 고성능 대안이지만 공식 native Windows 지원이 없어 기본값에서 제외한다. OpenCV/Pillow는 CPU 전체 프레임 접근 때문에 제외한다.

## 결정 5: writable 출력과 수명

**결정**: 렌더러는 런타임이 명시적으로 writable로 제공한 프레임만 수정한다. 그렇지 않으면 풀에서 별도 GPU 출력 프레임을 받아 인코더까지 수명을 유지한다.

**근거**: DLPack 텐서는 생산자 메모리를 공유하므로 무조건적인 in-place 변경은 안전하지 않다. 출력 소유권과 완료 이벤트를 계약으로 표현해야 한다.

**검토한 대안**: 디코드 surface의 무조건 직접 수정은 가변성과 encoder 호환성을 가정하므로 제외한다.

## 결정 6: 모델 배포와 검증

**결정**: 저장소에는 모델 파일을 넣지 않고 모델 계약, 준비 절차와 설정 예시를 제공한다. 단위·계약 시험은 CPU 전환 금지와 수명을, 실제 GPU 시험은 장치 전송·지연·메모리 및 30분 실행을 측정한다.

**근거**: 모델 라이선스와 크기를 분리하고, API 표면이 아닌 측정으로 무복사를 입증할 수 있다.

**검토한 대안**: 자동 다운로드는 네트워크·공급망 의존성을 만들고, FPS만 측정하면 숨은 복사와 동기화를 발견하지 못한다.
