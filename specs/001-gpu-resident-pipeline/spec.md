# 기능 명세: GPU 상주 단일 스트림 파이프라인

**기능 브랜치**: `생성되지 않음`

**작성일**: 2026-09-08

**상태**: 초안

**입력**: 사용자 설명: "GPU-resident single-stream pipeline"

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 단일 비디오 스트림 처리 (우선순위: P1)

운영자는 하나의 비디오 입력을 시작하고, 각 프레임이 디코딩부터 인코딩까지 GPU에
상주한 상태로 순서대로 처리되어 출력되는 파이프라인을 실행한다.

**우선순위 선정 이유**: GPU와 CPU 사이의 전체 프레임 왕복 없이 단일 스트림을 완주하는
것이 이 기능의 핵심 가치이자 다른 기능의 기반이다.

**독립 테스트**: 알려진 프레임 수와 순서를 가진 입력 하나를 처리하여 출력 프레임 수와
순서가 일치하고, 정상 경로에서 전체 프레임의 GPU → CPU → GPU 왕복이 0회임을 확인한다.

**인수 시나리오**:

1. **Given** 지원되는 형식의 단일 비디오 입력과 유효한 처리 구성이 주어졌을 때,
   **When** 운영자가 파이프라인을 시작하면, **Then** 모든 입력 프레임이 순서대로 디코딩,
   전처리, 추론, 후처리 및 인코딩되어 하나의 출력 스트림으로 전달된다.
2. **Given** 정상 처리 중인 스트림이 있을 때, **When** 프레임 데이터 경로를 관찰하면,
   **Then** 전체 프레임 픽셀 데이터는 모든 단계에서 GPU에 상주하고 GPU → CPU → GPU
   왕복은 발생하지 않는다.
3. **Given** 입력의 끝에 도달했을 때, **When** 파이프라인이 종료되면, **Then** 처리 중인
   모든 프레임이 완료된 뒤 리소스가 해제되고 완료 상태가 보고된다.

---

### 사용자 스토리 2 - 독립적인 알고리즘 구성 (우선순위: P2)

알고리즘 개발자는 외부 Python 모듈로 제공한 전처리, 추론 또는 후처리 구성요소를 다른
단계나 핵심 런타임을 변경하지 않고 교체하여 단일 스트림에 적용한다.

**우선순위 선정 이유**: 비디오 전송과 GPU 리소스 관리를 안정적으로 유지하면서 사용자별
알고리즘을 적용할 수 있어야 파이프라인을 실제 분석 작업에 활용할 수 있다.

**독립 테스트**: 세 단계 중 한 단계만 대체 구성요소로 바꾸어 실행하고, 나머지 단계의
구성과 런타임 변경 없이 예상 출력과 GPU 상주 경로가 유지되는지 확인한다.

**인수 시나리오**:

1. **Given** 계약을 충족하는 사용자 제공 알고리즘 구성요소가 있을 때, **When** 해당
   구성요소를 한 처리 단계에 지정하면, **Then** 다른 단계의 변경 없이 로드되어 프레임을
   처리한다.
2. **Given** 사용자 구성요소가 GPU 상주 프레임에 접근할 때, **When** 프레임 처리가
   완료되면, **Then** 구성요소는 기반 GPU 리소스의 소유권을 획득하거나 임의로 수명을
   변경하지 않는다.
3. **Given** 계약을 충족하지 않는 구성요소가 지정되었을 때, **When** 파이프라인 시작을
   요청하면, **Then** 프레임 처리를 시작하지 않고 원인을 식별할 수 있는 오류를 보고한다.

---

### 사용자 스토리 3 - 부하와 성능 상태 관찰 (우선순위: P3)

운영자는 실행 중인 단일 스트림의 지연 시간, 처리량, 메모리 사용량, GPU/CPU 전송,
동기화 지점 및 큐의 역압 상태를 관찰하고 성능 회귀를 재현한다.

**우선순위 선정 이유**: 무복사와 성능에 대한 주장은 관찰 가능한 증거가 있어야 검증되고
운영 중 문제를 진단할 수 있다.

**독립 테스트**: 고정된 입력과 처리 구성을 반복 실행하여 필수 측정값이 기록되고 동일한
조건에서 성능 결과를 재현할 수 있는지 확인한다.

**인수 시나리오**:

1. **Given** 파이프라인이 실행 중일 때, **When** 운영자가 실행 상태를 조회하면,
   **Then** 프레임 처리량, 단계별 지연 시간, 메모리 사용량, 전송 및 동기화 정보와 큐
   상태를 확인할 수 있다.
2. **Given** 하류 단계가 입력 속도를 따라가지 못할 때, **When** 전용 프레임 큐가 용량
   한계에 도달하면, **Then** 구성된 역압 정책이 적용되고 제어 플레인은 계속 명령과 오류를
   전달한다.
3. **Given** 동일한 입력, 구성 및 실행 환경이 준비되었을 때, **When** 성능 검증을 반복하면,
   **Then** 기준 결과와 비교 가능한 지연 시간, 처리량 및 메모리 사용량 결과가 생성된다.

### 경계 사례

- 입력 스트림이 프레임을 일시적으로 제공하지 않으면 파이프라인은 제한 없이 버퍼를
  늘리지 않고 대기 상태를 보고한다.
- 손상되거나 지원되지 않는 프레임을 만나면 해당 오류와 처리 위치를 보고하고, 구성된
  오류 정책에 따라 스트림을 안전하게 중단한다.
- 하류 처리가 장시간 정체되면 제한된 큐와 역압 정책으로 GPU 메모리 증가를 제한한다.
- 입력 종료와 중지 명령이 동시에 발생하면 새 프레임 수락을 중단하고 이미 수락된 프레임의
  처리 여부를 일관된 종료 정책에 따라 결정한다.
- 사용자 알고리즘이 프레임을 보유한 채 반환하지 않거나 동기화 계약을 위반하면 오류를
  보고하고 해당 리소스를 안전하지 않은 상태로 재사용하지 않는다.
- GPU 리소스 할당 또는 장치 실행이 실패하면 부분 출력과 처리 상태를 보고하고 모든 소유
  리소스를 안전하게 정리한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 동시에 하나의 입력 비디오 스트림을 받아 디코딩 → 전처리 → 추론 →
  후처리 → 인코딩 순서로 처리해야 한다.
- **FR-002**: 시스템은 수락한 프레임의 순서를 보존하고 입력 프레임과 출력 프레임의 처리
  상태를 추적할 수 있어야 한다.
- **FR-003**: 정상 경로의 전체 프레임 픽셀 데이터는 모든 처리 단계에서 GPU에 상주해야
  하며 GPU → CPU → GPU 왕복이 발생해서는 안 된다.
- **FR-004**: 시스템은 `GpuFrame`을 파이프라인의 표준 프레임 표현으로 사용하고 소유권,
  수명, 형식, 장치 및 동기화 요구사항을 보존해야 한다.
- **FR-005**: CPU 호스트 메모리의 이미지 버퍼는 전체 프레임 픽셀 데이터의 주 파이프라인
  표현으로 사용되어서는 안 된다.
- **FR-006**: 핵심 파이프라인은 특정 GPU 공급업체, 운영체제 또는 그래픽 API의 구체 형식에
  의존해서는 안 되며, GPU별 동작은 백엔드 경계 안에 격리되어야 한다.
- **FR-007**: 시스템은 프레임 데이터에 전용의 제한된 큐, 풀 또는 스트리밍 경로를 사용하고
  큐 용량 도달 시 명시적인 역압 정책을 적용해야 한다.
- **FR-008**: 전체 프레임 픽셀 데이터는 제어 플레인 이벤트를 통해 전달되어서는 안 된다.
- **FR-009**: 제어 플레인은 명령, 구성, 수명 주기 이벤트, 오류, 메트릭 및 추론 메타데이터를
  데이터 플레인의 정체와 독립적으로 전달할 수 있어야 한다.
- **FR-010**: 시스템은 전처리, 추론 및 후처리용 외부 Python 구성요소를 각각 독립적으로
  교체할 수 있어야 한다.
- **FR-011**: 사용자 제공 구성요소는 정의된 런타임 계약을 따라야 하며 기반 GPU 리소스의
  소유권이나 수명 주기 관리를 요구해서는 안 된다.
- **FR-012**: 사용자 제공 구성요소는 지원되는 무복사 상호운용 방식으로 GPU 상주 데이터에
  접근할 수 있어야 하며 정상 경로에서 전체 프레임의 GPU → CPU 전송을 요구해서는 안 된다.
- **FR-013**: 파이프라인 런타임은 비디오 전송, GPU 리소스 관리, 스케줄링, 동기화, 역압 및
  수명 주기를 관리해야 한다.
- **FR-014**: 시스템은 시작 전 입력, 출력, 처리 단계 및 사용자 구성요소의 계약 호환성을
  검증하고 실패 원인을 보고해야 한다.
- **FR-015**: 시스템은 GPU/CPU 전송, 동기화 지점, 버퍼 소유권, 단계별 및 전체 지연 시간,
  처리량, 메모리 사용량과 큐 상태를 측정할 수 있어야 한다.
- **FR-016**: 무복사 상태는 실제 프레임 전송 관찰 결과로 판정해야 하며 API 표면만으로
  판정해서는 안 된다.
- **FR-017**: 시스템은 고정 입력과 구성으로 반복 가능한 성능 검증 결과를 생성하고 기준
  결과와의 차이를 식별할 수 있어야 한다.
- **FR-018**: 시스템은 정상 종료 시 수락된 프레임의 처리를 마무리하고, 중단 또는 실패 시
  소유 중인 GPU 리소스를 안전하게 정리하며 최종 상태를 보고해야 한다.

### 주요 엔터티

- **파이프라인 실행**: 단일 입력 스트림의 시작부터 종료까지를 나타내며 구성, 상태, 처리
  카운트, 시작·종료 시각 및 오류 결과를 가진다.
- **GpuFrame**: GPU 상주 비디오 프레임으로서 프레임 식별자, 순서, 형식, 크기, 장치,
  소유권, 수명 및 동기화 요구사항을 가진다.
- **처리 단계**: 디코딩, 전처리, 추론, 후처리 또는 인코딩 역할과 입출력 계약을 나타낸다.
- **알고리즘 구성요소**: 전처리, 추론 또는 후처리 단계에 연결되는 사용자 제공 모듈과 그
  호환성 및 수명 주기 상태를 나타낸다.
- **프레임 큐**: 단계 사이의 제한된 데이터 경로로서 용량, 점유량 및 역압 상태를 가진다.
- **성능 측정 결과**: 특정 입력, 구성 및 환경에서 수집한 전송, 동기화, 지연 시간, 처리량,
  메모리 사용량 및 큐 상태의 집합이다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 정상 완료한 검증 실행의 100%에서 디코딩부터 인코딩까지 전체 프레임의
  GPU → CPU → GPU 왕복 횟수가 0회이다.
- **SC-002**: 알려진 입력으로 실행한 검증의 100%에서 수락된 프레임의 순서가 유지되고,
  누락·중복·손상된 출력 프레임이 0개이다.
- **SC-003**: 30분 연속 부하 검증 동안 프레임 큐 사용량은 구성된 용량을 초과하지 않고,
  GPU 메모리 사용량은 준비 구간 이후 지속적인 증가 추세를 보이지 않는다.
- **SC-004**: 입력이 합의된 운영 프레임 속도 이하일 때 30분 검증 실행에서 처리량은 입력
  속도의 99% 이상을 유지한다.
- **SC-005**: 동일한 입력, 구성 및 실행 환경에서 5회 반복한 성능 검증의 처리량과 95백분위
  지연 시간은 중앙값 대비 각각 ±5% 범위에서 재현된다.
- **SC-006**: 전처리, 추론 또는 후처리 중 한 단계만 교체하는 모든 계약 검증에서 핵심
  런타임과 나머지 단계의 변경 없이 실행이 완료된다.
- **SC-007**: 부하 및 오류 검증의 100%에서 제어 명령과 오류 상태가 전체 프레임 데이터와
  분리되어 전달되고, 전체 프레임이 제어 플레인에 게시된 사례가 0건이다.
- **SC-008**: 정상 종료, 운영자 중지 및 처리 실패 검증의 100%에서 실행은 유한 시간 안에
  최종 상태를 보고하고 소유 GPU 리소스를 남기지 않는다.

## 가정

- 첫 번째 릴리스는 한 번에 하나의 입력과 하나의 출력으로 구성된 단일 스트림만 다룬다.
- 입력과 출력 형식은 선택된 실행 환경이 지원하며, 지원 여부는 처리 시작 전에 확인된다.
- 입력 프레임 속도, 큐 용량, 역압 정책 및 종료 정책은 실행 구성에 명시된다.
- 기본 역압 동작은 프레임을 암묵적으로 버리지 않고 상류 수락을 제한하는 것이다.
- 추론 메타데이터는 전체 프레임 픽셀 데이터를 포함하지 않는 소량의 구조화된 데이터이다.
- 로깅과 메트릭은 프레임 식별자와 집계값을 포함할 수 있지만 전체 프레임 픽셀 데이터는
  포함하지 않는다.
- 전체 프레임의 CPU 접근 예외는 이 기능 범위에 포함하지 않으며 별도 명세와 승인이 필요하다.
- 성능 기준 비교에서는 입력, 구성, 장치 및 실행 환경을 동일하게 유지한다.
